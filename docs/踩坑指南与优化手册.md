# Mify 造数工厂 — 踩坑指南与优化手册

> 适用于比赛讲解 / 技术分享

---

## 一、项目背景

造数工厂是一个基于 OpenClaw + mify 工作流的自动化造数 Skill，用于在测试环境自动创建 SCM 采购申请（PR）→ 审批 → 转 PO → 推 ERP 的完整链路。

核心挑战：**SCM / BPM / 数据库均在内网，只能通过 mify HTTP 工作流代理访问。**

---

## 二、架构总览

```
用户（飞书对话）
  ↓
OpenClaw（AI Agent）
  ↓
造数引擎 engine.py（YAML 编排 + Jinja2 模板）
  ↓
mify 平台（HTTP 工作流 / SQL 工作流）
  ↓
SCM / BPM / MySQL（内网服务）
```

---

## 三、踩坑指南

### 坑 1：SQL Streaming 模式极慢（60s/次）

**现象**：每次 SQL 查询耗时 60 秒，5 次 SQL 调用共耗时 5 分钟。

**原因**：mify SQL 工作流使用 streaming 模式时，逐行推送 SSE 事件，1000 行结果 = 1000 个 SSE 事件串行发送。

**修复**：改用 blocking 模式，一次性返回完整 JSON。

```python
# 改前
"response_mode": "streaming"
# 改后
"response_mode": "blocking"
```

**耗时对比**：`60s → 15s`（4 倍提升）

**注意**：blocking 模式的 input 参数名必须是 `db_uri`（下划线），不是 `dbUri`（驼峰），否则 400 报错。

---

### 坑 2：Blocking SQL 参数名陷阱

**现象**：blocking 模式返回 `"url is required in input form"` 或 `"method is required"`。

**原因**：尝试用 `dbUri`（驼峰）替代 `db_uri`（下划线），mify 工作流无法识别。

**修复**：

```python
# ❌ 错误
"inputs": {"dbUri": db_uri, "query": query}

# ✅ 正确
"inputs": {"db_uri": db_uri, "query": query}
```

**教训**：mify 工作流的 input key 是固定的，必须与工作流定义完全一致。

---

### 坑 3：SCM Create PR 返回 400

**现象**：调用 `POST /mrp/pr/ordinary` 始终返回 `status_code: 400`。

**原因**：
1. Cookie 过期 — SCM 的 CAS Cookie 有效期短
2. Cookie 被 mify 环境拒绝
3. 请求体格式问题 — 模板渲染的 JSON 可能有字段缺失

**当前处理**：fallback 到 SQL 查询最新 PR 号（兼容旧 PR 复用）。

---

### 坑 4：PR 转 PO 报错「明细行已被删除」

**现象**：`pr_to_po` 返回 `code: 20010000, message: 选择转PO的明细行已被删除`。

**原因**：`create_pr` 返回 400 → fallback SQL 找到旧 PR → 旧 PR 已经被转过 PO → 明细行已删除。

**本质**：不是引擎 bug，是**测试数据状态问题**。同一个 PR 不能重复转 PO。

---

### 坑 5：mify HTTP 工作流固有开销（45s/次）

**时间分解**：

| 环节 | 耗时 | 能优化吗 |
|------|------|----------|
| 身份校验 + 限流 | 1-2s | ❌ |
| 创建 workflow run | 2-3s | ❌ |
| 冷启动容器 | 15-20s | ❌ 平台限制 |
| 实际 HTTP 请求 | 3-10s | ✅ 取决于目标服务 |
| SSE 事件流推送 | 5-10s | ⚠️ blocking 可减少 |
| 响应数据回传 | 2-3s | ❌ |

**结论**：45s 中约 20s 是冷启动，10s 是 SSE 开销。除非拿到内网直连权限，否则无法绕过。

---

### 坑 6：Cookie 获取方式

**现象**：mify HTTP 工作流无法访问 Cookie 服务。

**解决**：本机 curl 直接获取 Cookie，跳过 mify 代理。

```python
cmd = ["curl", "-s", "--connect-timeout", "10", cookie_url]
result = subprocess.run(cmd, capture_output=True, text=True, timeout=15)
cookie = json.loads(result.stdout)["data"]["result"]["cookie"]
```

---

### 坑 7：ASL 校验耗时且非必须

**现象**：ASL 校验通过 mify HTTP 调用，2 个物料串行校验需 60s+。

**分析**：ASL 校验只是检查物料-供应商关系，不影响后续 PR 创建。SCM 后端自己也会校验。

**决策**：从 ZNB 流程中移除 ASL 校验步骤，节省 30s+。

---

### 坑 8：等待时间过长

**优化**：

| 步骤 | 原等待 | 优化后 |
|------|--------|--------|
| query_pr_info | 8s | 2s |
| approve_pr | 8s | 3s |
| approve_po | 8s | 3s |
| query_erp | 5s | 2s |

---

### 坑 9：并行循环执行

**修复**：给 loop 步骤加 `parallel: true`，使用 `ThreadPoolExecutor` 并行执行。

```yaml
check_asl:
  action: loop
  parallel: true
  items: "{{inputs.materials}}"
```

**效果**：2 个物料从 90s → 45s。

---

### 坑 10：进度不可见

**修复**：
1. FlowEngine 加 `progress_callback` 回调
2. 每步输出 `__PROGRESS__:⏳/✅ 标记`
3. `run_with_feishu.py` 包装器解析标记并推送飞书消息

## 四、优化手册

### 优化总览

| 优化项 | 改动文件 | 节省时间 |
|--------|----------|----------|
| SQL blocking | `lib/client.py` | ~225s |
| 删除 ASL | `configs/*.yaml` | ~30s |
| 减少等待 | `shared/common-steps.yaml` | ~20s |
| 并行执行 | `lib/flow.py` | ~45s |
| 进度推送 | `lib/flow.py` + `run_with_feishu.py` | 体验优化 |

**总计**：421s → 233s（快 45%）
